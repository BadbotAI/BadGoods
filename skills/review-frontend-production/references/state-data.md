# 状态、数据与异步行为审查

按本手册检查页面在真实数据、连续操作、会话变化和后台任务下是否仍表达正确事实。先读取项目实际路由、请求层、状态管理、接口契约和组件使用方式，再选择适用检查；不要把框架或某个状态机库当成生产门槛。

沿用 [ledger-contract.md](ledger-contract.md) 的实体、关系和覆盖规则。把页面关联到 `PAGE-`，把共享定义关联到 `DEF-`，把使用实例关联到 `CMP-`，把场景、检查、证据、发现和实施任务分别关联到 `SCN-`、`CHK-`、`EV-`、`FND-`、`TASK-`。不要另建一套 JSON 字段或状态词表。

## 1. 建立状态与数据边界

为每个页面列出以下状态来源，并写清拥有者、寿命、更新触发、持久化位置和失效条件。

| 来源 | 查明内容 | 优先排查 |
|---|---|---|
| 服务器事实 | 实体、版本、权限、任务状态、规范化结果 | 是否被本地计时器或成功 Toast 代替 |
| URL 状态 | 资源 ID、筛选、分页、排序、可分享视图 | 是否与组件内另一份状态失同步 |
| 用户草稿 | 未保存字段、选中文本、暂存配置 | 是否被后台刷新覆盖或串到另一实体 |
| 临时 UI 状态 | 展开、焦点、弹窗、拖动、悬停 | 是否意外跨页面共享或该保留时被销毁 |
| 派生状态 | 计数、可操作性、有效性、组合文案 | 是否可以计算却保存了多个副本 |
| 外部过程 | 订阅、轮询、流式输出、上传、后台运行 | 是否与页面生命周期错误绑定 |

先写业务不变量，再检查实现。例如要求“显示的详情属于当前 URL 的实体”“正式结果只能来自已确认提交”“租户切换后不得继续显示前一租户的缓存”。

将互斥状态表达为有限的合法取值；将可并存的维度分开。例如允许“任务运行中 + 日志断线 + 取消请求待确认”，不要把三者压成一个相互排斥的开关。

列出可达状态与关键迁移，覆盖初始、等待、成功、失败、中断、恢复和失效条件。不要要求无意义的全量笛卡尔积；优先检查会破坏不变量的组合，并说明省略组合的原因。

区分“原型未实现的既定范围”和“在承诺范围内行为错误”。仅凭存在 `useState`、未使用 Redux、文件较长或没有状态机库，不要登记缺陷。

## 2. 审查路由与浏览器历史

对每个可访问 `PAGE-` 验证菜单进入、直接 URL、刷新、前进、后退和新标签页进入；按实际范围检查嵌套路由、弹窗路由、部署子路径和服务器回退配置。

- 让详情页从资源身份重建所需数据；检查是否只依赖上一个页面传来的临时对象。
- 校验路径和查询参数；对非法 ID、未知枚举、负页码、越界页码、编码字符和过期游标给出确定行为。
- 指定 URL 与本地状态的唯一拥有者；检查筛选变化后是否重置失效分页，以及控件值、地址和数据是否一致。
- 指定哪些变化创建历史记录，哪些只替换当前记录；避免每次输入字符都制造难以使用的返回路径。
- 区分不存在、已删除、无权限、待登录、加载失败；保存用户可恢复的目标地址，但不要允许未校验的外部重定向。
- 从长列表进入详情后返回，检查筛选、排序、选择与滚动位置是否按承诺恢复。
- 对未保存编辑定义离开行为；结合草稿保存或导航拦截，不把一个 `beforeunload` 弹窗当成可靠持久化。
- 检查权限变化和实体删除后，旧历史项是否仍暴露缓存或可执行操作。

将“返回不方便”与“返回后提交错实体”等不同影响分开登记；按具体用户损失排序。

## 3. 审查共享状态与组件身份

绘制实际的数据拥有与消费关系，不要按屏幕上的视觉分组推断共享边界。

- 对同一实体在列表、详情、弹窗和顶部统计中的副本建立关联；检查一次更新是否会产生不一致。
- 为选择状态优先保存稳定身份，再从权威数据解析；只有需要冻结快照时才有意复制对象，并说明版本语义。
- 检查排序、插入、删除、分页和虚拟列表后的身份稳定性；当存在重排或行内状态时，重点审查索引 key、随机 key 和重复 key。
- 不要把所有索引 key 一律判错；对真正静态、不会重排且无身份敏感状态的列表，记录适用前提即可。
- 切换实体、工作区或模式时，逐项定义保留、重置、迁移和重新校验哪些状态；不要靠偶然挂载位置决定。
- 检查组件定义是否嵌在渲染函数内导致反复卸载；检查受控值与默认值是否混用，外部更新是否被初次初始化吞掉。
- 对全局 store、context、单例 client 的生命周期核对租户与会话边界；不要只为减少 props 传递而扩大数据寿命。
- 将多个订阅者共同需要的数据与某个实例独有的编辑草稿分开，防止一个实例的关闭/清空影响其他实例。

对共享 `DEF-` 与所有已知 `CMP-` 保留影响映射。证明共享代码有缺陷，不等于已经复现每个页面实例的影响。

## 4. 审查表单与编辑草稿

对每个表单记录加载基线、当前草稿、已提交快照与服务器确认值；以具体值追踪保存前后发生了什么。

| 场景 | 要求检查的结果 |
|---|---|
| 异步默认值到达 | 不无提示覆盖已经输入的内容；不把默认值误当正式保存 |
| 切换上游字段 | 重算选项与有效性；清除或迁移不再适用的下游值 |
| 隐藏或禁用字段 | 明确是否提交；不让隐藏旧值改变业务行为 |
| 数值输入中间态 | 允许合理编辑过程；不要把空值、负号、科学计数法编辑中间态错误提交 |
| 服务器字段错误 | 映射到正确字段，保留草稿，给出修复入口并管理焦点 |
| 后台刷新与编辑并存 | 提示基线变化；区分本地未保存改动与服务器新值 |
| 多人/多窗口保存 | 检测版本冲突；避免无提示覆盖他人的更新 |
| 提交中继续编辑 | 让响应只确认对应提交快照，不误清除之后新增的改动 |
| 离开后恢复草稿 | 按用户、租户、实体、版本隔离；迁移或舍弃失效结构 |
| 提交后再次打开 | 显示服务器实际接受的结果，包括规范化值和默认补全 |

按成本决定是否需要自动保存、撤销、跨设备草稿和冲突合并；不要给简单表单强加完整协同编辑系统。

审查本地持久化中的敏感字段与保留期限；需要登录后恢复的草稿不能无条件留给下一位使用同一浏览器的人。

核对前端即时校验与后端最终校验的职责。不要以“按钮禁用了”作为业务约束已得到保护的证据。

## 5. 审查数据契约与运行时边界

对每个接口查明请求字段、响应字段、错误结构、可空性、枚举、单位、时间格式、分页语义和版本；将 Mock 与真实契约逐项核对。

- 区分零、空字符串、缺失、`null`、未知与尚未计算；检查 `value || fallback` 是否吞掉有效零值。
- 校验科学计数法、精度、整数边界、秒/毫秒、百分数/比例、时区和日期范围；集中转换与格式化规则。
- 将外部 JSON、URL 参数、持久化草稿、消息事件视作运行时输入；依据风险检查真实解析/校验路径。
- 不得从 `.ts` 文件、`as Foo`、非空断言或生成出的客户端类型推断运行时数据已经验证。TypeScript 静态类型不校验网络返回值。
- 在不可信或高影响边界采用适当运行时校验；沿用项目已有方案。不要要求每个内部对象重复解析，也不要为了形式新增多个校验库。
- 区分结构校验与业务合法性：字段类型正确，不代表数据集仍可访问、余额足够或当前状态允许该操作。
- 对未知枚举、新增可选字段、字段重命名、旧客户端、新服务器和过期草稿给出兼容策略；不要让未知状态自动落入“成功”。
- 明确数据集/模型/配置引用的是最新版本、固定版本还是提交快照；保证预览与执行引用可核对。
- 检查接口是否只能提供阶段，却由前端伪造精确总进度；缺少数据能力时登记后端契约依赖。
- 对契约缺失只记录已观察字段和待确认项，不编造后端字段或接口；为阻塞关键行为的缺口创建可归责 `TASK-`。

若建议 OpenAPI、JSON Schema 或类型生成，说明要解决的具体漂移问题及接入位置；不要把存在描述文件当成契约测试已通过。

## 6. 审查读取与错误恢复

为数据区域区分首次加载、有效空结果、已有数据刷新中、刷新失败与不可访问；按业务依赖拆开失败范围。

- 检查 `fetch` 的 HTTP 状态与响应解析；不要把只有 `try/catch` 视为已处理 4xx/5xx。
- 区分网络失败、超时、取消、认证失效、权限不足、业务校验和服务器故障；依据接口语义提供恢复动作。
- 区分“最后已知数据”与“当前已确认数据”；刷新失败时可保留旧数据，但要按风险标注陈旧状态与操作限制。
- 检查独立接口是否被不必要地串行等待，或因一个失败导致整页不可用；同时保留真正的数据依赖顺序。
- 检查筛选、排序、统计的计算范围；只加载当前页时，不声称对全部记录完成了筛选、排序或计数。
- 定义当前页全选、跨页已选与全部匹配结果全选；条件变化后核对选中集合、可见反馈和批量操作范围。
- 检查删除最后一条、空页、总数变化、重复记录、游标失效和迟到分页响应；避免跳页、丢项与重复项。
- 按操作语义决定重试；不要自动重试永久参数错误，或将不确定是否完成的写入当普通读取重发。

对读取故障保留具体 `EV-`：请求条件、响应状态、页面表现、恢复步骤和最终结果。证据中隐藏凭据和无关个人数据。

## 7. 审查竞态与副作用生命周期

用可控制的延迟交换两个请求的完成顺序，检查实现是否把“最后返回”错误当成“当前需要”。

| 竞争关系 | 检查约束 |
|---|---|
| 搜索 A 后搜索 B，A 更晚返回 | 当前输入与结果仍对应 B |
| 详情 A 切到详情 B | A 的响应、错误和 Toast 不覆盖 B |
| 筛选变化与翻页同时发生 | 旧条件的页结果不混入新列表 |
| 自动保存连续两次 | 较旧提交不覆盖较新编辑；服务器也处理写入顺序 |
| 后台刷新与乐观修改 | 旧快照不无提示抹掉当前待确认操作 |
| 卸载后事件继续到达 | 释放订阅与计时器；事件不写入错误页面 |

检查 effect 依赖、闭包读取、事件处理器、轮询重入、订阅重建和资源清理。保留有明确目的的 effect；将用户这次点击产生的提交放在对应动作路径，避免因挂载或状态同步意外重发。

允许通过请求身份、查询库、路由数据层、过期响应过滤或取消实现正确性；检查实际行为，不强制手写某种通用 hook。

明确浏览器取消的边界：`AbortController` 可停止客户端等待/读取，但不能保证服务端未执行或撤销已执行动作。对业务写入另外审查服务端幂等、版本或顺序控制。

## 8. 审查写入与乐观操作

对每个创建、保存、删除、启动、停止、重新生成操作，列出“待发送、等待确认、确认成功、确认失败、结果未知”的处理方式；不必使用这些字面状态名，但必须能解释相应事件。

### 重复提交、超时与结果未知

- 复现连点、键盘重复提交、多标签页和超时后重试；不要把禁用按钮作为去重的全部方案。
- 区分“请求明确失败”与“服务端已执行但响应丢失”；后者保留提交身份，并按协议查询或恢复结果。
- 对高影响写入与服务端约定幂等范围、有效期和相同键不同载荷的处理；同一次意图重试复用身份，新的用户意图使用新身份。
- 检查幂等性是否由服务器保证；前端生成随机 ID 或存一个布尔值本身不提供保证。
- 对批量操作明确全成功、部分成功和单项失败；重试失败项时避免重复执行成功项。

### 乐观更新与并发回滚

- 先判断是否适合提前展示成功；对收费、权限、训练终止等动作优先表达“正在处理/等待确认”，直到相关事实得到确认。
- 为每次 mutation 保留独立身份、作用实体与待确认值；区分列表插入、字段编辑、删除与批量操作。
- 检查失败回滚是否会用一个旧的全量快照覆盖之后已成功的修改；对同一实体并发采用串行、按操作撤销、重放待确认操作或重新获取并合并等合适策略。
- 将服务器规范结果与本地临时 ID、排序、计数和详情缓存对齐；确认待确认标记在成功、失败和未知结果路径都能结束或恢复。
- 对版本冲突保留用户草稿；依据产品选择重新加载、比较、合并或重试，不静默接受最后写入覆盖。

为每个动作写出成功判据，例如“服务器返回创建实体身份”或“后台报告终态”，不要统一使用“Promise resolve”。

## 9. 审查缓存身份与多租户切换

列出每个查询的数据身份：租户/工作区、用户权限范围、实体 ID、资源版本、筛选、排序、分页/游标和结果表示。只纳入实际决定结果的维度，但不要漏掉身份隔离维度。

- 检查相同 key 是否可能取到不同数据；检查不同 key 是否重复保存本应一致的同一结果。
- 切换工作区、退出登录、切换账号或权限降低时，处理缓存展示、待处理请求、订阅和持久化缓存；不要只换页面标题。
- 为写入列出受影响读取：列表、详情、汇总、关联选择器、配额和权限；规定精确更新、失效重取或重新验证策略。
- 核对新鲜度、垃圾回收、窗口聚焦重取、网络恢复重取、轮询和持久化；采用符合实际数据变化速度的策略。
- 对表单隔离服务器缓存与编辑草稿；缓存自动刷新不应无提示覆盖用户编辑。
- 对缓存尚未获取过、实体已删除、权限已撤销和旧版本仍被引用的情况，定义明确结果。
- 仅在需求存在时设计跨标签页广播、离线队列和跨设备同步；不要将这些能力列成所有页面的默认门槛。

把错误租户缓存与服务器授权分别检查。正确的缓存键不能替代服务器权限检查，服务器权限正确也不保证前端不会显示前一会话残留数据。

## 10. 审查会话与权限刷新

复现页面打开期间凭据过期、权限降低和账号切换；检查数据、操作与恢复目标是否同步变化。

- 对多个请求同时遇到过期，检查是否产生刷新风暴、重复登录弹窗或无限重试；按实际认证协议组织一次刷新与等待请求恢复。
- 刷新后确认请求仍属于原授权用户/租户；若会话已切换，不回放前一身份的待处理动作。
- 对非幂等写入，不因重新认证就自动重发结果未知的请求；先按提交身份核实原操作结果。
- 区分需要重新认证与已无权限；无权限不能靠重复刷新令牌解决。
- 保留可安全恢复的草稿与目标页；限制敏感缓存和跨身份草稿泄漏。
- 当服务器仍未提供操作级权限或版本校验时，登记接口缺口；不要用隐藏按钮作为替代修复。

遵循用户现有会话和工具权限，不为审查额外探测无关账号，不输出令牌、Cookie 或刷新凭据。

## 11. 审查后台作业与取消

将请求、业务作业、实时连接与产物分别建模。不要把 HTTP 已受理、作业已创建、开始执行与最终成功混成一个结果。

- 为训练、导出、解析、导入和生成保留稳定作业身份；通过 URL 或持久引用恢复状态，避免刷新后重新创建任务。
- 根据真实协议区分排队、准备、执行、验证、产物处理、失败、取消中与终态；只使用后端能够证实的阶段。
- 定义整体成功的业务条件；若计算完成但结果上传失败，明确分别显示什么、哪些产物可用、重试从何处开始。
- 把任务阶段、连接状态、取消请求状态和产物可用性作为可独立成立的维度；检查有效组合。
- 提交取消后等待服务端确认；处理“取消与完成同时发生”“取消被拒绝”“取消结果未知”，不要直接伪装成已停止。
- 对进度没有总量依据时展示阶段或已处理量；不要用本地计时器生成看似精确的百分比。
- 对轮询、SSE 或 WebSocket 明确终态停止条件、退避、可见性策略、重连和补拉；不要让离页后继续创建订阅。
- 将日志、指标和产物绑定到具体运行/尝试身份；同一任务重试后不能混入上一次执行的事件。
- 对删除任务、删除记录、删除产物、取消执行和重试分别定义语义，防止一个“删除”按钮隐含多个副作用。

为后端缺少的取消确认、幂等、事件游标或产物查询创建独立任务；允许前端先提供诚实的待确认/断线状态，但不要宣称端到端问题已解决。

## 12. 审查流式 AI 交互

仅对实际存在的聊天、生成、工具调用或 Agent 过程加载本节；按协议检查，不假设所有产品都采用 SSE。

| 场景 | 检查行为 |
|---|---|
| 字符或 JSON 跨网络块 | 使用支持增量解码与协议分帧的解析；不把一个 chunk 当一条完整消息 |
| 重连、重放和重复事件 | 根据消息/运行/事件身份去重或续传；检测缺口并恢复 |
| 用户切换会话 | 旧流不写入新会话；后台是否继续由产品与服务端协议决定 |
| 用户停止生成 | 区分停止展示、断开传输和服务端取消；保留部分内容与实际结束原因 |
| 网络中断 | 将未完成结果标为中断或待恢复；不把连接关闭自然当完整成功 |
| 重新生成/编辑后续问 | 明确替换、分支还是追加；避免旧回复覆盖新的分支 |
| 工具调用部分到达 | 未收齐/验证参数前不执行；将调用、结果和失败绑定同一身份 |
| 工具动作重试 | 复用后端幂等/结果查询；不重复发送消息、付款或启动真实任务 |
| 长输出与历史增长 | 控制渲染/缓存增长与订阅寿命；不因重渲染重建整段流 |
| 最终事件到达 | 使用协议的完成、拒绝、截断、取消或错误原因收束状态 |

检查流式 Markdown、链接、代码和结构化数据的安全呈现；结合可访问性检查控制播报频率、焦点与滚动。不要为了滚动到最新内容打断用户阅读历史。

若展示 token、费用、耗时或工具执行轨迹，说明数据来源与暂估/最终口径；不得编造精确消费或把模型文本当服务器执行证明。

## 13. 组织故障场景与验收

从用户目标与不变量构造 `SCN-`，并把具体动作、可观察结果与恢复结果拆成 `CHK-`；将源码、网络记录、截图或自动化输出关联为 `EV-`。

按场景协议填写 `preconditions`、非空 `steps`/`expected`、`context`、`risk` 与关联 ID；在 `context` 说明相关角色、数据、网络、视口、输入方式和生命周期，不适用则解释。沿用场景状态 `planned/passed/failed/blocked/not_applicable`，不要把检查的 `not_checked` 用作场景状态。

对实际取得的证据填写 `kind/locator/observed_at/baseline_ref/summary`；将接口约定归为 `specification`，将截图等输入归为 `artifact`，不要将它们当成运行通过。把待执行验证写进任务 `verification_scenario_ids`，把已执行证据写进 `evidence_ids`；不能只凭源码让异步场景通过。

先检查具备明显风险的单因素，再加入高影响组合：

1. 延迟与乱序响应；提交成功但响应丢失；请求明确被拒绝。
2. 反复点击、跨实体切换、刷新、返回和新标签页打开。
3. 正在编辑时后台刷新；两个标签页编辑同一版本。
4. 租户切换与旧请求返回；会话过期与待确认写入并存。
5. 作业完成与取消同时发生；流式输出中断、重放和恢复。
6. 批量操作部分成功；分页范围变化与跨页选择并存。

在已有授权的测试环境、可回放 Mock 或隔离数据上复现。涉及真实收费、发送消息、删除资源或启动训练时，沿用当前授权和工具政策；不要为普通读取或可逆本地复现添加无条件审批，也不要假定审查请求授权所有生产副作用。

没有可运行环境时记录静态证据和阻塞场景；将高风险未知项安排为先行验证任务，不把推测标为已复现。需要组件方案时选择 `investigate`，在 `BP-` 的当前/目标合同中标明待确认部分，并为每个受影响实例保留独立补证计划；不要假造确定重构或以 `retain` 代替缺证据。

完成后逐项回答：当前页面是否知道数据属于谁、是哪一版、何时确认、操作是否完成、失败如何恢复。将仍需后端配合的结果保留为未闭合依赖。
