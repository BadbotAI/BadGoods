# UI 用例走查

> 确认输入 → 侦察并拆解组件 → 建模输入与状态 → 设计用例 → 用户确认 → 逐条执行取证 → 判定 → 报告 → 复盘沉淀。

## 适用范围

| 适用 | 不适用（最多做基础检查，并在报告「未覆盖项」注明） |
|---|---|
| 网页、H5、SPA、管理后台的功能与交互走查 | 性能压测、容量测试 |
| 小程序、App（手动执行或截图走查） | 安全渗透、攻击性测试 |
| 只有截图、设计稿时的静态走查 | 接口自动化、单元测试 |
| 修复后的回归走查 | 全量浏览器/设备兼容矩阵 |

## 核心原则

1. **先对齐再执行**：链接、范围、环境未确认时不开始设计和执行；用例清单必须经用户确认（预授权规则见 Step 5）。
2. **依据优先**：每条预期结果都要能追溯到需求文档、页面文案、无障碍标签或通用约定；无依据的标「推断」。
3. **证据说话**：判定基于页面快照、截图、控制台报错和网络请求，不凭印象。
4. **生产只读**：不得在生产环境执行写入、删除、支付、发送消息等操作。
5. **不确定就标注**：「待确认」「未执行」「阻塞」都不是「不通过」，也不是「通过」。
6. **去重**：同类场景只保留最有代表性的用例，不为凑数量造用例。
7. **风险驱动**：用例数量按风险和走查深度分配，先 P0，再 P1、P2。
8. **数据安全**：只用虚构的测试数据；截图或日志里出现真实个人信息、手机号、Token、密钥时打码或不保存。

## 输入与产出

| 项 | 要求 |
|---|---|
| 必须输入 | 页面链接、截图或设计稿（至少一种）；本次走查范围 |
| 建议输入 | 需求文档、测试账号、测试环境、浏览器/设备要求、上次走查报告（回归时） |
| 产出 | 侦察结论、页面-组件清单、用例清单、执行结果、截图证据、Markdown 走查报告 |

缺目标或范围时先问用户，不要猜测目标页面或业务范围。需要问的问题一次问全，不要一个一个挤牙膏。

## 走查模式

Step 1 根据输入和用户意图选定一种，写进清单和报告头部。

| 模式 | 什么时候用 | 产出 |
|---|---|---|
| 设计 | 只要用例；或暂时没有可访问的环境 | `case-list.md` |
| 自动执行（默认） | 有可访问的 URL 和浏览器工具 | `case-list.md` + 截图 + `report.md` |
| 手动执行 | 小程序、App、内网、需要真机，或没有浏览器工具 | 逐条操作清单 → 用户回填 → `report.md` |
| 静态走查 | 只有截图或设计稿 | 按组件清单和页面五态逐项检查，报告标注「仅静态，未交互验证」 |
| 回归 | 用户给了上次报告或缺陷清单 | 重跑缺陷关联用例 + 受影响的 P0，输出与上次的对比 |

## 走查深度

用户没说时默认「标准」。数量是参考，以风险为准。

| 深度 | 覆盖 | 参考规模 |
|---|---|---|
| 冒烟 | P0 主流程和致命风险 | 每页 3–8 条 |
| 标准 | P0 + P1，6 类核心类别中适用的都覆盖 | 每页 10–30 条 |
| 深度 | 再加 P2、扩展类别、账号/设备/环境矩阵 | 不设上限，但必须去重 |

## 工作产出目录

在用户工作目录下创建：

```text
walkthrough/<目标>-<YYYYMMDD>/
├── case-list.md            # 侦察结论 + 页面-组件清单 + 用例清单（Step 5 检查点交付物）
├── report.md               # 走查报告
├── screenshots/            # 证据截图，文件名以用例编号开头
│   └── TC-001-login-empty.png
└── raw/                    # 控制台日志、网络记录、页面快照等原始记录（可选）
```

用例编号 `TC-001` 起连续编号，缺陷编号 `D-001` 起；截图文件名以用例编号开头，便于报告反查。

## 工作流

按顺序执行，不要跳过检查点。

### Step 1 — 确认输入

确认：目标（链接/截图/设计稿）、需求文档（可选）、测试账号、测试环境、本次范围（哪些页面/功能、不包含什么）、设备与视口、走查模式、走查深度。

- 缺目标或范围 → 停下来问用户。
- 需要登录但没账号 → 问用户要测试账号或已登录会话；拿不到时，登录后的用例标「阻塞」，只走查登录前页面。
- 环境是生产 → 只做只读检查，并在报告里说明限制。
- 测试账号要区分角色，每个角色都是一个数据维度：正常账号、新用户（无数据）、有大量数据的账号、无权限/低权限账号、锁定/禁用账号。练习站或演示环境如果提供了故意带缺陷的账号，单独记录，判定时归为「预设缺陷」。
- 记录目标环境（URL、账号、浏览器/视口、执行时间），写进报告头部。

### Step 2 — 侦察与拆解

**2a 只读侦察**：先看清页面再设计，不提交任何会写入数据的操作。

- 打开页面，读取页面快照，必要时截图。
- 识别页面类型：表单页、列表页、详情页、多步骤流程、内容页、登录/鉴权页。
- 记录：可见组件、可跳转的链接和路由、是否需要登录、首屏网络请求（状态码）、控制台报错。
- 无法访问的部分（需登录、需权限、需真机）写进「待确认」。
- 在 `case-list.md` 写 3–8 条「侦察结论」。

**2b 拆解组件**：读取 `references/components.md`，逐页面列出组件，为每个组件写：

- **用途**：这个组件让用户完成什么。
- **预期行为的依据**：需求文档条款、页面文案/占位符、无障碍标签，或通用约定。没有依据的标「推断」。

| 页面 | 组件 | 类型 | 用途 | 预期行为的依据 | 依据来源 |
|---|---|---|---|---|---|
| 登录页 | 用户名输入框 | 输入框 | 输入账号 | 必填（页面文案）；区分大小写（推断） | 页面文案 / 推断 |

### Step 3 — 建模

读取 `references/test-design.md` 和 `references/page-states.md`，逐页面识别：

- **输入**：每个输入的有效/无效等价类，以及边界值（三值法：边界及其两侧）。
- **条件组合**：多个条件共同决定结果时，必须输出决策表；组合太多时用两两组合缩减。没有多条件场景，在报告里写「无多条件场景」。
- **页面状态**：理想、空、加载、错误、部分数据五种状态。不适用或无法触发的状态写进「未覆盖项」并说明原因，不能默认为已覆盖。
- **状态流转**：关键流程的状态与触发事件，包含非法流转：返回、刷新、重复提交、会话过期、多标签页并发。
- **需求追溯**（有需求文档时）：每条需求至少对应一条用例，没有对应的写进「未覆盖项」。

建模结果不必单独成文，但必须体现在用例的前置条件和预期结果里。

### Step 4 — 设计用例

读取 `references/test-design.md`、`references/heuristics.md`、`references/pitfalls.md` 和 `assets/case-template.md`。

**核心类别**（每个组件覆盖适用的）：

1. 正常流程
2. 等价类（有效/无效）
3. 边界值
4. 错误与异常
5. 状态流转
6. 中断与并发（连点、刷新、返回键、断网、多标签页）

**扩展类别**（深度走查必做；标准走查只在明显相关时加）：

- 无障碍：键盘可达、焦点顺序、错误提示与输入框的关联、图标按钮的可读名称
- 视图与兼容：窄屏、200% 缩放、长内容、移动端软键盘
- 文案与内容：错别字、误导性文案、提示是否说清下一步
- 权限与数据安全：未登录拦截、越权访问、敏感信息展示（只读观察，不做攻击性测试）

每条用例字段：

| 编号 | 页面/组件 | 类别 | 优先级 | 前置条件 | 步骤 | 预期结果 | 依据 | 执行方式 |
|---|---|---|---|---|---|---|---|---|

执行方式取值：`自动`、`手动`、`需授权`（会发短信、支付、删除等）、`需账号`、`仅静态`。

优先级：

- **P0**：主流程，或涉及数据丢失、资金、权限、隐私。
- **P1**：常见异常、高频操作的错误处理。
- **P2**：体验细节、低频场景。

用 `references/heuristics.md` 和 `references/pitfalls.md` 查漏后，再按走查深度控制数量。不适用某类时不要硬造用例。

### Step 5 — 检查点（必须）

把「侦察结论 + 页面-组件清单 + 用例清单 + 待确认问题」写入 `case-list.md`，发给用户确认。

- 默认：**用户明确回复「确认/可以/执行」后才进入执行。**
- 预授权：用户事先明确说过「不用确认，直接执行」，可以直接执行「自动」「手动」类用例；「需授权」的用例仍要逐项询问。在报告头部记录预授权的原话和范围。
- 用户调整范围时先更新清单，不要边执行边改清单。清单确认前只做只读观察，不产生判定。

### Step 6 — 执行

边执行边对照 `references/pitfalls.md`。

浏览器工具按以下顺序选择：

1. 当前会话已有的 Playwright MCP / 浏览器工具（以实际工具名为准，如码道 MCP 市场的 Playwright-MCP）。
2. 已安装的 `playwright-cli`（先 `playwright-cli list` 复用已有会话）。
3. 都没有时安装：`npm install -g @playwright/cli@latest`，用 `playwright-cli --help` 确认命令，必要时 `playwright-cli install-browser`。
4. 仍不可用 → 改为「手动执行」模式：生成逐条操作清单让用户执行并回填，报告标注「未使用真实浏览器执行」。

单条用例的执行循环：

```text
重置到已知状态 → 打开/定位页面 → 读取快照 → 操作 → 再读快照 → 截图存证
→ 对照预期判定 → 记录本条用例相关的控制台报错与网络请求
```

`playwright-cli` 通用模式（命令细节以 `playwright-cli --help` 为准）：

```bash
playwright-cli list                                  # 先复用已有会话
playwright-cli -s=ui-walkthrough open "<url>"
playwright-cli -s=ui-walkthrough resize 1440 900
playwright-cli -s=ui-walkthrough snapshot            # 获取页面结构与元素 ref
playwright-cli -s=ui-walkthrough screenshot --filename "walkthrough/.../screenshots/TC-001-xxx.png"
playwright-cli -s=ui-walkthrough eval "document.querySelector('#id').value"   # 兜底读取/断言
playwright-cli -s=ui-walkthrough close
```

执行规则：

- **顺序**：先 P0，再 P1、P2。时间或额度受限时，记录已完成范围。
- **证据**：每条用例至少一张截图，覆盖「操作后」状态，异常用例截异常现场；关键中间态也要留证。控制台和网络检查绑定到具体用例，不能用一次全局检查代替。
- **隔离**：每条用例开始前重置到已知状态（账号、业务数据、Cookie/localStorage、URL、筛选和排序），避免上一条污染下一条。
- **执行失败不是用例结果**：元素 ref 失效、脚本报错、误点导航时，先恢复上下文再重试，并在报告中记录重试。
- **模拟要真实触发目标行为**：
  - 连点：真实双击，或两次点击间隔 ≥100ms；同一 tick 的两次 JS click 不算。
  - 断网/弱网：选有网络请求的动作（登录、提交、搜索），并用网络记录确认请求确实失败或变慢；工具不支持时标「未执行」。
  - 接口错误/空数据：工具支持路由拦截时，用拦截返回 500、超时或空列表；不支持时标「未执行」。
  - 移动端：用视口模拟（如 375×812）时，在报告注明「模拟，非真机」。
- **判定前先归因**：区分「产品缺陷」「预设缺陷」「环境/平台行为」，三者不混为一谈。
- **记录要点**：校验类记录输入值、实际提示文案、`aria-invalid`/错误样式、是否清空已填内容；状态类记录 URL、页面标题、登录态、数据是否还在。
- **停下来问**：遇到验证码、短信、支付、删除、发送消息、发布等不可逆或需要真人的操作。
- 无法判断是否为缺陷 → 标「待确认」；条件不具备（无账号、无法模拟）→ 标「未执行」并写原因。

### Step 7 — 判定

每条用例标记五种状态之一：

| 状态 | 含义 |
|---|---|
| 通过 | 实际结果与预期一致，且确实触发了要验证的路径 |
| 不通过 | 可稳定复现的偏差，记为缺陷 |
| 阻塞 | 前置条件或环境导致无法继续，原因明确 |
| 未执行 | 条件不具备，未操作 |
| 待确认 | 行为可疑，但无法判定是否符合需求 |

不通过记为缺陷，字段：标题、复现步骤、预期与实际、严重程度、截图、控制台报错、失败请求、复现概率、**归因（产品缺陷/预设缺陷/环境行为）**、**置信度（高/中/低）**。

判定纪律：

- 依据充分的明确偏差判「不通过」，不要用「待确认」回避判断。例如：输入首尾空格导致校验失败、计数角标与实际条目数不一致、报错后清空了用户已填内容。
- 练习站或演示环境故意注入的缺陷，归「预设缺陷」，不计入产品通过率。
- 静态托管、CDN、网关造成的 404、重定向、缓存行为，先归「环境行为」，除非能证明是应用逻辑问题。
- 证据不足时才用「待确认」，并写清缺什么证据、需要谁确认。
- 演示环境没有真实资金和隐私数据时，严重程度按「如果发生在生产会怎样」评估，并在报告中说明。

严重程度：

- **致命**：数据丢失或损坏、资金错误、越权、隐私泄露、核心流程完全不可用。
- **严重**：主流程受阻但有绕过方式、状态错乱、重复提交产生脏数据。
- **一般**：非主流程功能异常、错误提示误导、边界处理不当。
- **建议**：文案、对齐、交互体验细节。

### Step 8 — 报告

按 `assets/report-template.md` 输出 `report.md`：

基本信息（含走查模式、深度、预授权范围）→ 摘要与结论 → 按账号/环境分层统计 → 缺陷清单（按严重程度排序，标注归因）→ 用例执行明细 → 误报与排除项 → 未覆盖项与原因 → 建议回归项 → 与上次基线对比（回归模式或有基线时）。

- 通过率分两个口径：产品通过率（排除预设缺陷和环境行为）和原始通过率，都要写。
- 报告必须能让没参与执行的人复核：每条不通过都有编号、步骤和截图路径。
- 结论一句话：是否建议上线/继续验收，主要风险是什么。

### Step 9 — 复盘

报告交付后必须执行：

1. 问用户这次有没有新发现的坑。
2. 自查：列出本次判断错、漏测、方法不可靠的地方。
3. 把以上内容整理成对本 Skill 的修改建议：写进 `references/pitfalls.md` 的新经验，或对 SKILL.md、其他 references、模板的修改。以「修改前/修改后」给用户看。
4. 用户确认后再写入；在 `references/changelog.md` 记一条（日期、改了什么、来源）。未确认的不要写入。

## 停止条件

出现以下情况先停下来问用户，不要自行继续：

- 目标或范围不明确，或需要登录但无可用账号。
- 用例清单尚未确认（预授权情况见 Step 5）。
- 需要执行不可逆或需要真人的操作（删除、支付、发送、发布、短信验证码）。
- 需要填写真实个人信息才能继续。
- 发现疑似致命缺陷（数据丢失、越权、资金错误、隐私泄露）。
- 环境不可达，且无法判断是网络、权限还是页面问题。

## 禁止事项

- 在生产环境执行写入操作。
- 对用户没有授权的第三方网站做走查，或发起大量请求。
- 使用真实个人信息作为测试数据；保存未打码的敏感信息截图。
- 把「未执行」「待确认」写成「通过」或「不通过」。
- 没有截图或快照证据就下结论。
- 伪造截图、日志、接口响应或测试数据。
- 把模型推测的需求写成「依据」；无依据必须标「推断」。
