# 测试设计方法

Step 3 建模、Step 4 设计用例时读取。每种方法给出一个可套用的例子。

## 1. 等价类划分

把输入域分成「结果应该相同」的若干类，每类取一个代表值。有效等价类证明功能可用，无效等价类证明错误被拦住。

步骤：

1. 列出输入的约束（类型、长度、格式、范围、是否必填）。
2. 划分有效等价类；对每个约束再划分无效等价类。
3. 每类取一个值，不重复覆盖。

例子：手机号输入框（11 位数字，1 开头）

| 类 | 取值 | 预期 |
|---|---|---|
| 有效 | `13800138000` | 通过校验 |
| 无效-长度不足 | `138001380` | 提示「请输入 11 位手机号」 |
| 无效-长度超长 | `138001380001` | 截断或提示 |
| 无效-非数字 | `1380013800a` | 提示格式错误 |
| 无效-非 1 开头 | `23800138000` | 提示格式错误 |
| 无效-空 | 空字符串 | 提示必填 |

## 2. 边界值三值法

对有序输入，取边界值及其两侧：`min-1 / min / min+1`、`max-1 / max / max+1`。长度、数量、金额、日期、页码都适用。

例子：昵称长度 2–20 个字符

| 值 | 长度 | 预期 |
|---|---|---|
| `a` | 1 | 报错（低于下限） |
| `ab` | 2 | 通过（下限） |
| `abc` | 3 | 通过（下限+1） |
| 19 个字符 | 19 | 通过（上限-1） |
| 20 个字符 | 20 | 通过（上限） |
| 21 个字符 | 21 | 报错（高于上限） |

补充检查：全空格、首尾空格、中文占几个字符、emoji 是否算 1 个、粘贴超长文本时输入框是否截断。

## 3. 决策表

多个条件共同决定一个结果时使用。列出条件桩、动作桩，再列出所有可行规则组合。

例子：优惠券能否使用

| 规则 | 已登录 | 订单满 100 | 券未过期 | 结果 |
|---|---|---|---|---|
| R1 | 是 | 是 | 是 | 可用，抵扣 |
| R2 | 是 | 是 | 否 | 不可用，提示已过期 |
| R3 | 是 | 否 | 是 | 不可用，提示未达门槛 |
| R4 | 否 | 是 | 是 | 跳转登录，登录后回到结算页 |
| R5 | 否 | 否 | 否 | 跳转登录（登录优先于其他校验） |

关注点：规则优先级（哪个错误先提示）、互斥条件、是否存在遗漏组合、条件变化后结果是否实时更新。

### 组合太多时：两两组合

条件多、取值多时，全组合会爆炸（如 4 个条件各 3 个取值 = 81 种）。大部分缺陷由一个或两个条件的组合触发，所以可以只保证「任意两个条件的每种取值搭配至少出现一次」，通常能把用例缩到十几条。

- 先用决策表列出有业务规则的组合（必须全测）。
- 剩下没有明确规则的组合（如浏览器 × 语言 × 账号类型），用两两组合挑选。
- 已知高风险的组合，额外单独加用例。

## 4. 状态流转

画出「状态 + 事件 → 新状态」。重点是非法流转和边界事件。

例子：订单状态

```text
待支付 --支付成功--> 已支付 --发货--> 已发货 --确认收货--> 已完成
待支付 --取消--> 已取消
已支付 --退款--> 退款中 --退款成功--> 已退款
```

必测的非法流转：

- 已取消订单再次支付
- 已发货订单取消
- 已完成订单退款
- 重复点击「支付」是否只生成一笔
- 支付中途返回/刷新，订单状态是否一致
- 两个标签页同时操作同一订单
- 会话过期后点「支付」是否跳登录且保留订单

## 5. 错误推测

基于经验列出最可能出错的点，作为前面方法的补充，不作为唯一依据。

常见来源：

- 空值、空格、超长、特殊字符、emoji、换行、SQL/HTML 片段
- 连点、快速切换、刷新、返回、关闭弹窗
- 弱网、断网、接口 4xx/5xx、超时、重复响应
- 权限：未登录、无权限角色、直接输入 URL
- 数据：0 条、1 条、刚好多一页、超长文本、图片加载失败
- 时间：跨天、时区、夏令时、有效期边界

写用例时注明这是「错误推测」，并在执行时确认实际行为。

## 需求追溯

有需求文档时使用，确保每条需求都被测到。

1. 把需求拆成可验证的条目，编号 R1、R2…（一条只说一件事）。
2. 每条需求至少对应一条用例；用例的「依据」写需求编号。
3. 没有对应用例的需求，写进报告「未覆盖项」并说明原因。
4. 需求前后矛盾或含糊（如「合理的长度」），列进「待确认」，不要自己定标准。

| 需求 | 内容 | 对应用例 | 状态 |
|---|---|---|---|
| R1 | 手机号为 11 位数字 | TC-004、TC-005、TC-006 | 已覆盖 |
| R2 | 未勾选协议不能登录 | TC-003 | 需授权 |

## 风险与优先级

优先级 = 出错后的影响 × 出错的可能性。

| | 可能性高（新功能、复杂逻辑、刚改过、历史多发） | 可能性低 |
|---|---|---|
| **影响大**（主流程、数据、资金、权限、隐私） | P0 | P0 / P1 |
| **影响小**（体验、文案、低频功能） | P1 | P2 |

走查深度为「冒烟」时只做 P0；回归时优先重跑缺陷关联用例和受改动影响的 P0。

## 用例字段写法

| 字段 | 要求 |
|---|---|
| 编号 | `TC-001` 连续编号 |
| 页面/组件 | 页面名 + 组件名，如「登录页 / 用户名输入框」 |
| 类别 | 核心：正常流程 / 等价类 / 边界值 / 错误与异常 / 状态流转 / 中断与并发；扩展：无障碍 / 视图与兼容 / 文案与内容 / 权限与数据安全 |
| 优先级 | P0 / P1 / P2 |
| 前置条件 | 登录态、数据状态、环境，写可复现的最小条件 |
| 步骤 | 他人能照做的编号步骤，包含具体输入值 |
| 预期结果 | 可观察、可判定；写清文案、状态、URL、数据变化 |
| 依据 | 需求编号 / 页面文案 / 无障碍标签 / 通用约定 / 推断 |
| 执行方式 | 自动 / 手动 / 需授权 / 需账号 / 仅静态 |

好用例与坏用例：

| 坏 | 好 |
|---|---|
| 测试手机号输入 | 输入 10 位数字 `1380013800` 后点登录 |
| 应该正常显示 | 显示「请输入 11 位手机号」，已填内容保留 |
| 检查各种异常 | 拆成多条：断网、接口 500、超时，各写预期 |

## 6. 测试方法与判定有效性

设计用例时同时设计「怎么模拟」：

- 连点：真实双击或 ≥100ms 间隔两次点击；同一 tick JS click 无效。
- 断网：选有网络请求的动作，并用 requests/console 确认请求确实失败。
- 并发：两个标签页/两个账号/两个会话，确认状态是否互相覆盖。
- 慢网/加载态：用 route delay、慢账号或节流，确认 loading 与禁用态。

判定前先问：这次操作真的触发了要验证的路径吗？没有触发就标「未执行」，不要标「通过」。

## 7. 账号与环境矩阵

同一功能在不同账号、设备、环境下可能是不同的等价类：

| 维度 | 取值示例 | 关注点 |
|---|---|---|
| 账号角色 | 正常、新用户（无数据）、大量数据、无权限、锁定/禁用 | 权限、空状态、分页、提示 |
| 预设缺陷账号 | 练习站/演示环境提供的故意带缺陷的账号 | 先用正常账号建基线，再逐个对比；归「预设缺陷」 |
| 设备与视口 | 桌面 1440×900、移动 375×812、窄屏 320 | 布局、点击区域、软键盘 |
| 浏览器 | Chromium（默认）、Safari/WebKit、微信内置浏览器 | 只在用户要求或有已知差异时扩展 |
| 环境 | 本地、测试、预发、生产（只读） | 静态托管与动态服务端分开判断平台行为 |

矩阵会让用例翻倍，标准深度下只让 P0 跑多个维度，其余用默认组合。
